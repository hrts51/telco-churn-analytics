1. Project Objective

Customer churn — when a subscriber cancels their telecom service — is a primary revenue risk. Acquiring a new customer typically costs significantly more than retaining an existing one, so understanding which customer and service attributes are associated with churn helps prioritise retention investment.

Primary objective: Analyse patterns in the IBM Telco Customer Churn dataset to identify which customer, service, and subscription attributes are most strongly associated with churn; quantify the monthly revenue exposure; and develop evidence-based retention recommendations.

Scope and constraints: - Descriptive and associative analysis only - Does not establish causation - Does not explain why any individual customer left - Does not constitute a predictive model - All findings are specific to this dataset

5. Data Cleaning

Notebook: notebooks/01_data_understanding.ipynb

The raw data was loaded into df. All cleaning was applied to a separate copy df_clean so the original was always preserved for comparison.

What was inspected first

Raw shape:   7,043 rows × 21 columns
Duplicate customerIDs: 0
Churned: 1,869  |  Retained: 5,174  |  Churn rate: 26.5%
TotalCharges blank values: 11

Cleaning decision 1 — TotalCharges conversion

Problem: TotalCharges was stored as a text column in the raw CSV. 11 rows contained blank or whitespace values instead of a number.

Investigation: Every one of the 11 blank rows had tenure = 0, meaning these customers had just signed up and had not yet been billed for a full month.

Decision: Convert TotalCharges to float. Fill the 11 confirmed zero-tenure blanks with 0.0. Do not drop any rows — these are valid, real customers.

Validation code run:

assert unexpected_invalid.sum() == 0      # no surprise non-numeric values
assert df_clean.loc[blank_charges, "tenure"].eq(0).all()  # all blanks are tenure=0

Result: 0 missing values in TotalCharges after cleaning.

Cleaning decision 2 — SeniorCitizenLabel

Problem: SeniorCitizen uses 0/1 encoding, which is not readable in charts.

Decision: Add SeniorCitizenLabel (No/Yes) alongside the original numeric column. Keep the original for arithmetic; use the label for display.

Cleaning decision 3 — Preserve original service labels

Decision: "No internet service" and "No phone service" labels were kept as-is. These values carry analytical meaning — a customer who has no internet service is fundamentally different from one who has internet but chose not to add security. Replacing these with blanks or a generic "No" would lose that distinction.

Cleaning decision 4 — No rows dropped

All 7,043 customers were retained. No rows were removed for any reason.

Clean file output

Saved: data/clean/telco_clean.csv
Shape: 7,043 rows × 25 columns
Missing TotalCharges: 0
Unique customerIDs: 7,043 (verified)

SELECT

Calculated columns (DAX)

ChurnFlag =

CLV_Proxy =
'telco_clean'[MonthlyCharges] * 'telco_clean'[tenure]

AddonCount =
(IF([OnlineSecurity]="Yes",1,0) + IF([OnlineBackup]="Yes",1,0) +
 IF([DeviceProtection]="Yes",1,0) + IF([TechSupport]="Yes",1,0) +
 IF([StreamingTV]="Yes",1,0) + IF([StreamingMovies]="Yes",1,0))

TenureSegment =
IF('telco_clean'[tenure] <= 12, "New",
   IF('telco_clean'[tenure] <= 36, "Growing", "Loyal"))

ChargeSegment =
IF('telco_clean'[MonthlyCharges] <= 35, "Low",
   IF('telco_clean'[MonthlyCharges] <= 65, "Mid", "High"))

HighRisk =
IF('telco_clean'[tenure] <= 12 && 'telco_clean'[MonthlyCharges] >= 65, 1, 0)

Core DAX measures

Total Customers = DISTINCTCOUNT('telco_clean'[customerID])

Churned Customers =
CALCULATE([Total Customers], 'telco_clean'[ChurnFlag] = 1)

Churn Rate = DIVIDE([Churned Customers], [Total Customers], 0)

Total Monthly Revenue = SUM('telco_clean'[MonthlyCharges])

Monthly Revenue Lost =
CALCULATE(SUM('telco_clean'[MonthlyCharges]), 'telco_clean'[ChurnFlag] = 1)

Churned Customer ARPU = DIVIDE([Monthly Revenue Lost], [Churned Customers], 0)

Retained Customer ARPU =
DIVIDE(
    CALCULATE(SUM('telco_clean'[MonthlyCharges]), 'telco_clean'[ChurnFlag] = 0),
    [Total Customers] - [Churned Customers],
    0
)

High-Risk Segment Customers =
CALCULATE([Total Customers], 'telco_clean'[HighRisk] = 1)

High-Risk Churn Rate =
DIVIDE(
    CALCULATE([Churned Customers], 'telco_clean'[HighRisk] = 1),
    [High-Risk Segment Customers],
    0
)

Monthly Revenue in High-Risk Segment =
CALCULATE(SUM('telco_clean'[MonthlyCharges]), 'telco_clean'[HighRisk] = 1)

# Recommendation Addresses

14. Limitations

  1. No causal inference — Cross-sectional observational data. Association ≠ causation.

  2. No time dimension — Single snapshot. Cannot observe trends or how churn rates changed over time.

  3. No exit reason data — The dataset does not include why customers left. Pricing complaints, service quality, competitor offers, and life events are all equally plausible explanations.

  4. Confounding — Attributes correlate with each other (Fiber Optic users are more likely to be on month-to-month contracts). Independent contributions cannot be isolated without a controlled model.

  5. No predictive validity — Segment churn rates describe the past. They should not be used to score individual customers without further validation.

  6. Synthetic dataset — This is an illustrative dataset from IBM. Its distributions may not match a real telecom company's customer base.

15. What Makes This Project Unique

Most Telco churn portfolio projects on the internet follow the same pattern: load CSV → plot a few charts → train logistic regression → print accuracy. This project is different in several ways.

1. Business-driven rule-based segmentation Instead of relying on a model score, a transparent high-risk segment was defined using rules any stakeholder can understand and audit. The definition is documented, justified, and deliberately updated during Power BI development with the reasoning recorded.

2. Revenue exposure quantification The project goes beyond churn rate to answer: how much money is at risk? $139,131/month, $81K in the high-risk segment alone. These are the numbers a CFO cares about, not a 26.5% rate.

3. Consistent metric definitions across three tools Every number in Python, SQL, and Power BI traces back to the same cleaned CSV with the same definitions. Query 30 in SQL explicitly reconciles against Python.

4. Honest analytical caveats throughout Every notebook, every SQL file, every Power BI page, and this documentation all carry the same caveat: associations, not causation. This is rare in portfolio projects and is what professional data work requires.

5. CLV proxy labelled correctly MonthlyCharges × tenure is labelled as a historical billed-value approximation, not a prediction. The difference matters.

6. SQL goes beyond GROUP BY CTEs, window functions (RANK, running totals), multi-way cross-tabs with minimum cell size filters, and a reconciliation query. 30 queries across 7 analytical groups.

7. Customer-level drill-down in Power BI Page 3 includes a filtered table of individual high-risk customers — not just aggregated charts. A retention team could use this directly.
